# 子项目 B 设计：语音管线（转写与发言人识别）

**状态**：草案，待用户审阅（2026-10-14）。关联总设计文档第 7 节（语音管线）、10.1（S4）、第 11 节（实施拆分）。本文细化第 7 节，并写明 S4 的做法与通过标准；与总设计冲突时以本文为准，并同步更新总设计。

## 1. 目标与边界

- **做什么**：每场录制保存后，在本机离线地把 `mic.mka`（我）和 `system.mka`（对方）转成带发言人标签的 `transcript.json`：“我”“发言人 1、2、3…”；之后可以改名、合并、重新聚类。
- **不做**（沿用总设计）：第一版不用显卡；不做实时转写；不用云端识别（云端只用于纪要，且只发文字，属于子项目 C）；不做跨会议自动认人（只存每个发言人的声纹质心向量，留给以后）。
- **约束**：不影响正在进行的录制；除首次下载模型外不联网，下载要经用户同意；不静默失败；不改动原始录音。
- **用户为 S4 定下的三件事（2026-10-14）**：
  1. 测试音频只用公开数据集，不碰用户自己的会议录音（用户的真实会议以后由用户自己读转写稿反馈，我不读其中的文字）；
  2. 60 分钟的会议，会后 30 分钟内要出转写稿（实时倍数不低于 2；保存后在后台低优先级跑，不影响用户用电脑）；
  3. 允许把官方预编译程序、候选模型和评测集下载到仓库之外的 `E:\gezi\tools\s4\`（校验哈希，不入库）。

## 3. S4 的设计

### 3.1 要回答的问题

1. 默认的识别引擎是哪个？（在 30 分钟预算内最准的那个。）
2. 说话人分离用哪个声纹模型，聚类阈值默认取多少？人数能不能判对？
3. 回声消除选 corti-aec、aec3，还是不做？
4. 要不要对用户开放“麦克风轨也分出多个人”（几个人共用一个麦克风的场合）？

### 3.2 工具路线

| 路线 | 做法 | 取舍 |
|---|---|---|
| **A（选）** 官方预编译命令行 + 自己写的评测脚本 | 下载 sherpa-onnx 官方发布的 Windows 程序，只解压、不安装；用 Node 脚本（不装任何第三方包）切段、调用、算指标 | 不需要编译；官方文件有 SHA-256；换模型只改命令行 |
| B Python 轮子 | `pip install sherpa-onnx` | 要安装第三方包并执行其代码，与“只解压、不安装”的做法不一致 |
| C 直接用 Rust 绑定写评测程序 | `sherpa-onnx` crate | 编译链（cmake、libclang）要先确认；留到 B2 再接 |

回声消除的两个候选是 Rust crate，用一个仓库之外的小 Rust 工程调用；编译前先看依赖树，确认没有 build 脚本下载东西、没有网络依赖。

### 3.3 评测数据：AliMeeting 评测集

- **来源与许可**：OpenSLR 119（阿里 M2MeT 挑战赛），CC BY-SA 4.0；下载地址取自 OpenSLR 页面。评测集 8 场会议，每场 15～30 分钟、2～4 人，真人讨论，含重叠说话；每位参会者一路近场头戴麦克风，另有 8 通道远场阵列；有逐字稿和说话人时间标注（TextGrid）。压缩包约 3.4 GB；**压缩包里是否确实含近场与远场两部分，解压后核对**，不符就在此处如实改。
- **每场会议构造三种输入**：
  - **“我”轨**：选一位参会者的近场录音，扮演麦克风轨；轮流选每位参会者。
  - **“系统”轨（干净混合）**：其余参会者的近场录音相加，扮演会议软件送来的对方声音。真实线上会议的音质介于“干净混合”和“远场”之间。
  - **远场**：远场阵列第 1 通道。比真实系统轨难，作为下界，也用来回答“共用麦克风”。
- **限制（如实写明）**：这是线下会议室里的普通话讨论，不是线上会议（没有会议软件的降噪与编码）；近场录音里有别人的串音，相加后同一个人的声音会出现多次。所以结果是**比较各候选的依据，不是对真实线上会议的保证**；真实会议的验收在 B 的最后一步，由用户读自己的转写稿。

### 3.5 指标与测法

- **识别**：字错误率 CER：参考与识别结果都去掉标点与空白、阿拉伯数字统一成汉字数字后逐字比较。先按标注的发言段切段（排除切段的影响），再单独跑一遍“VAD 自动切段”的端到端。记录 RTF（处理耗时 / 音频时长）、线程数 8 与 4 两档、峰值内存、模型加载时间。
  - **速度预选**：每个候选先在 3 场会议各 5 分钟上量 RTF；比预算慢 2 倍以上的不再跑全量准确率（只记录速度和这 15 分钟的 CER）。
- **分离**：DER（容差 0.25 秒，计重叠；漏检、误检、说话人混淆三项分列）；人数误差。“干净混合”和“远场”各测一遍；声纹模型 × 阈值（0.3～0.9，步长 0.1），以及已知人数两种做法。
- **回声消除**：合成回声：“系统”轨做远端，“我”轨做近端，混入延迟 20～300 ms、混响时间 0.2～0.6 秒的回声和低噪声；回声与近端语音的能量比取 −10、0、+5 dB 三档。指标：远端单讲段的回声消减量（ERLE）；近端失真（处理前后近端 CER 的变化）；回声插入率（远端单讲段里“我”轨识别出的字数 / 远端实际字数）。
  - **限制**：合成回声不等于真实的喇叭、房间与麦克风；真实外放回声需要一次真实场景的验证（要用户配合：放声音、不戴耳机）。这一步在做之前标为**未验证**。
- **整条流水线的时间估算**：用实测 RTF 和评测集里实测的说话占比，估算两条各 60 分钟音轨的总耗时（解码、回声消除、分离、识别、合并）。评测集的说话占比比一般会议高，估算偏保守。

### 3.6 通过标准（测之前写死，测完不放宽）

| 项 | 门槛 |
|---|---|
| 识别准确（近场，按标注切段，合计） | CER ≤ 15% |
| 速度与内存 | 估算 60 分钟会议 ≤ 30 分钟（8 线程）；峰值内存 ≤ 4 GB |
| 分离（干净混合） | DER ≤ 25%；估计人数与实际相差不超过 1 的场次 ≥ 6/8 |
| 开放“麦克风轨也分人” | 远场 DER ≤ 30% 才开放，否则 v1 不开放 |
| 回声 | 回声插入率 ≤ 5%，近端 CER 比无回声时增加 ≤ 2 个百分点；达不到就不做回声消除，提示“外放时请戴耳机” |

没有候选达标时**不降低门槛**：如实报告数字，由用户决定。

### 3.7 决策规则

- 默认识别引擎：满足速度与内存的候选里 CER 最低者；CER 相差在 0.5 个百分点内的取更快的。
- 声纹模型与阈值：干净混合上平均 DER 最低的声纹模型；阈值取在最低点附近、DER 相差不超过 1 个百分点的区间的中点（避免只适合这 8 场）。
- 回声消除：满足门槛的候选里近端失真最小者；都不满足则不做。

### 3.8 产物、清理与顺序

- **产物**：本文 3.9 写明数字与决策；评测脚本入库于 `scripts/s4/`（只含脚本，不含数据与模型）；候选模型清单草稿（名称、官方地址、SHA-256、许可、体积）作为 B2 的 `models.lock.json` 的输入。
- **不入库**：评测集、模型、识别结果、中间音频；全部放在 `E:\gezi\tools\s4\`，S4 结束后由用户决定保留还是删除。
- **下载与校验**：官方发布页的 `checksum.txt` 先用 GitHub API 给出的摘要校验，再用它校验各模型；没有官方摘要的文件（如 pyannote 分割模型、评测集）记录首次计算的 SHA-256，并如实标注“无官方摘要”。
- **顺序**：下载与校验 → 60 分钟长跑结束后才开始任何推理（长跑要求机器安静）→ 速度预选 → 全量准确率 → 分离 → 回声 → 写回决策。

## 4. 引擎方向（B2～B4，S4 的结果出来后再细化）

- **进程与协议**：沿用总设计 7.1 与 7.4：独立的 sidecar 进程，标准输入输出上的 JSON 行；命令 `process`、`pause`、`resume`、`cancel`，事件 `progress`、`done`、`error`。
- **流水线**：沿用 7.2。补充：分块处理，每块结果追加写入 `transcript.partial.jsonl`，崩溃或关机后从断点继续；两轨按 `session.json` 里的各轨起点对齐到会议时间。
- **资源**：进程降到后台优先级；线程数默认取核数的一半、最多 8；新录制开始时暂停，保存后继续。
- **模型管理**：`models.lock.json` 记录名称、官方地址、体积、SHA-256、许可；首次使用经用户同意下载到 `%LOCALAPPDATA%\record\models\`，校验后原子改名；失败明确报错、可重试，不悄悄跳过。
- **数据**：`transcript.json` 沿用 7.3 的结构；`diarization.cache` 缓存段级声纹向量；`session.json` 增加转写状态与所用引擎。
- **测试**：仓库不放音频（许可与体积）；回归测试用合成信号，真实数据的测试用环境变量指向本地数据集并标 `#[ignore]`；协议用假引擎测。

## 5. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 公开数据是线下会议，不是线上会议 | S4 的数字比真实线上会议乐观或悲观都有可能 | 干净混合与远场给出上下界；真实验收由用户读自己的转写稿 |
| 模型许可（FunASR 系、FireRedASR、Qwen3-ASR 等各有各的许可） | 分发受限 | S4 逐个核对；仓库不分发模型，只给官方地址与哈希 |
| sherpa-onnx 的 Rust crate 的构建依赖（是否构建时下载预编译库、是否要 cmake） | B2 编译链不确定 | B2 开头先确认；必要时固定版本并校验库的哈希 |
| 蓝牙等设备的播放延迟让外放回声的延迟超出回声消除器的范围 | 回声没消掉或消过头 | S4 的延迟扫到 300 ms；真实验证另做 |
| 中英夹杂、专有名词、标点质量 | 转写稿可读性 | S4 只量字错误率；标点与中英夹杂留给用户读转写稿时反馈 |
| 与新录制争抢 CPU | 录制掉帧或丢音 | 后台优先级；新录制开始时暂停 |
