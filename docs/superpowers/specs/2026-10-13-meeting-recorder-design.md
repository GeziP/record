# 会议录屏软件 · 设计文档

- 日期：2026-10-13（以系统时间为准）
- 工作名：`record`
- 状态：设计已确认，可进入实施计划（含补充调研，见第 15 节）
- 目标平台：Windows 11 x64（开发机为 Windows 11 build 26200）

## 1. 目标

做一个**独立于任何会议软件**的 Windows 常驻小工具：

1. 按热键开始，**静默**录下屏幕画面和声音（对方的声音 + 我的声音，分轨保存）；
2. 再按热键保存并结束，程序继续待命；
3. 事后在**本地**转写、区分发言人（我 / 发言人 1、2、3…，可手动改名）；
4. 可选地生成会议纪要。

设计时参考了开源项目和热门软件：读了 OBS Studio 的采集与封装源码；用 [REA](https://github.com/morluto/rea)（原生程序部分配合 Ghidra）对 Notion、夸克网盘、NVIDIA ShadowPlay，以及 Loom、tl;dv、Jamie、Granola 等同类桌面应用做了静态分析；还读了开源项目 OpenWhispr 在 Windows 系统音采集上遇到的问题与修复（见第 15 节）。

## 3. 范围

**v1 包含**：热键启停；整屏画面 + 系统音 + 麦克风分轨录制；收尾生成 MP4；崩溃恢复；托盘与设置；本地转写与发言人区分；改名与合并；纪要、检索、导出（按子项目分期交付，见第 11 节）。

**v1 不包含**：实时字幕；云同步；按窗口录制；鼠标指针叠加（Desktop Duplication 不带指针，后续可补）；自动检测会议开始；跨会议声纹库；macOS / Linux；暂停 / 恢复。

## 4. 总体架构

### 4.1 进程模型

- **常驻主进程**（Rust + Tauri v2）：托盘、全局热键、状态机、采集编排、会话存储、后台任务。网页界面按需创建窗口。
- **ffmpeg 子进程**（录制时拉起）：视频、麦克风、系统音各一个，各写一个崩溃安全的 Matroska 文件。
- **`speech-sidecar` 子进程**（处理时拉起）：基于 sherpa-onnx，录制结束后离线处理，低优先级，只用 CPU。

隔离的原因：录制是最不能出错的路径。编码器或语音引擎崩溃、占满资源，都不能影响采集。

### 4.2 模块（Rust workspace，最终 crate 划分在实施计划里定）

| 模块 | 职责 |
|---|---|
| `capture` | 采集屏幕、麦克风、系统音；只负责产出带 QPC 时间戳的数据 |
| `mux` | 时间线修复、写入 ffmpeg、收尾、崩溃恢复 |
| `session` | 会话目录与 `session.json` |
| `shell` | 托盘、热键、控制器、配置、窗口 |
| `jobs` | 后台任务队列（子项目 B 起持久化到 SQLite） |
| `speech` | 语音引擎协议与 sidecar |

### 4.3 会话目录

默认位置 `%USERPROFILE%\Videos\Record\`，首次运行向导里让用户选择：

```text
2026-10-13_203000/
  session.json      元数据：起止时间、各轨起点 QPC、诊断计数、状态
  video.mkv         画面（H.264，无声）
  mic.mka           麦克风（FLAC，无损）
  system.mka        系统音（FLAC，无损）
  meeting.mp4       收尾后生成：画面 + 混音（AAC），日常回放用
  transcript.json   转写稿（子项目 B）
  summary.md        纪要（子项目 C）
```

分轨落盘的理由：语音引擎直接使用无损分轨，识别更准，并天然得到“我 / 其他人”；任何一轨出问题都不拖累其他轨；收尾时按各轨起点时间对齐。

- 日志：`%LOCALAPPDATA%\record\logs\`，按天滚动
- 模型：`%LOCALAPPDATA%\record\models\`

## 5. 录制内核

### 5.1 统一时钟

所有数据用 QPC（`QueryPerformanceCounter`，换算为 100ns 单位）打时间戳。

- `t0_session` = 热键按下时的 QPC。
- 每轨的 `t0_stream` = 该轨第一份数据的 QPC，记入 `session.json`。
- 收尾时，每轨的偏移 = `t0_stream` − 所有轨 `t0_stream` 的最小值。

采集阶段只存**原始音频**，不做降噪、回声消除或自动增益。后期处理算法升级后，可以对旧录音重跑。

### 5.2 画面

- **采集**：DXGI Desktop Duplication。没有黄色捕获边框，适合静默。OBS 默认也走 Desktop Duplication，只在多显卡或显示器匹配不上时才改用 Windows Graphics Capture（WGC）。
- **失效处理**：每个 tick 以 0 超时调用 `AcquireNextFrame`；返回 `WAIT_TIMEOUT` 就沿用上一帧；返回 `DXGI_ERROR_ACCESS_LOST`（显示模式变化、UAC、锁屏等）就销毁并重建复制对象，重建尝试要节流（OBS 的间隔常量是 3 秒，本设计初值 1 秒，由 S2 调定）。
- **哪块屏**：按下热键时前台窗口所在的显示器；设置里可固定某一块；录制中不切换。
- **帧率**：恒定 15 fps（可设 10 / 15 / 30）。由 QPC 驱动的定时器，每个 tick 取最近一帧；屏幕无变化就重复上一帧，编码器几乎不花码率。视频帧序号 = floor((now − t0) × fps)，落后则复制上一帧补齐。
- **分辨率**：输出固定为开始时的值，长边 ≤ 1920、短边 ≤ 1080，保持宽高比，宽高取偶数。中途显示模式变化时，按比例缩放并加黑边，输出尺寸不变。
- **GPU 路径**：缩放和 BGRA → NV12 转换在 GPU 上由 D3D11 视频处理器完成，读回 CPU 的只有 NV12（1080p 约 3 MB/帧）。开发机是 4K@240Hz、看起来约 150% 缩放，全分辨率 BGRA 帧约 33 MB，15 fps 下读回 CPU 约 500 MB/s，代价过高，所以这是必须而不是优化。
- **编码**：ffmpeg 的硬件 H.264 编码器。启动时探测，顺序为 NVENC → QSV → AMF。都没有时明确报错；软件编码只能由用户在设置里显式选择，不会悄悄降级。
- **不抓取的内容**：UAC 安全桌面、锁屏、受保护内容抓不到，属于系统限制，不绕过。这段时间重复上一帧并记录区间，重复帧按原因分类计数（安全桌面 / 复制对象重建 / 复制失败，见 5.9；Loom 的录制进程就是这样分类统计的）。
- **不做静默降级**：Loom 的录制进程里，除了统计项名为 “data duplication” 的路径（推断即 Desktop Duplication），还带有一个 GDI 视频源，是否用作兜底没有确认。本设计不做自动兜底：失败就重复上一帧、告警、计数；WGC 能否作为明确提示后的备选后端，由 S2 评估。
- **HDR**：S2 判定。检测到 HDR 输出时，在日志和托盘里告警。候选方案三选一，结果写回本文：① 要求用户使用 SDR；② Desktop Duplication 用 `DuplicateOutput1` 请求 FP16（scRGB）格式，自己做色调映射到 SDR（OBS 的 Desktop Duplication 路径就是同时请求 `R16G16B16A16_FLOAT` 与 `B8G8R8A8_UNORM`，并带 HDR 标志）；③ WGC 加“强制 SDR”（OBS 的 WGC 路径提供这个选项）。S2 同时评估 WGC 能否无黄色边框采集，作为 Desktop Duplication 是否唯一后端的依据。

### 5.3 系统音（对方的声音）

- WASAPI 回环（loopback）采集默认播放设备，共享模式、事件驱动。
- 固定请求 48 kHz / float32 / 立体声，并设置自动格式转换，由系统引擎负责重采样，这样切换耳机、扬声器、HDMI 后格式不变。
- 监听默认设备变化（`IMMNotificationClient`），自动重连到新设备，空档按 5.5 补静音。
- 回环采集在“没有任何声音播放”时不出数据，见 5.5。
- **默认设备的两个角色**：Windows 区分“默认设备”（`eConsole`）和“默认通信设备”（`eCommunications`），部分会议软件会使用后者。OBS 的做法是桌面音取 `eConsole`、麦克风取 `eCommunications`。本设计的系统音默认 `eConsole`；S1 实测两个角色指向不同设备时是否漏录，若会，则按下表的方案 C 同时回环两个设备并去重。
- **自动格式转换需要验证**：OBS 没有设置自动转换，而是取设备的混音格式再自行重采样。本设计要求系统转换，S1 需验证回环流能这样打开；打不开就改用 OBS 的做法。
- **回环方案有四个候选，S1 实测后定**。上面几条都是在方案 A 的前提下写的：

| 方案 | 做法 | 已知特点 |
|---|---|---|
| A 默认播放设备回环（初始方案） | 对 `eConsole` 默认播放设备开回环，共享模式 | OpenWhispr 的实测里能听到 Teams（见 15.6，本机待 S1 复验）；只听默认设备，会议声音走别的设备就漏录；切换默认设备要重连 |
| A2 默认通信设备回环 | 对 `eCommunications` 设备开回环 | 两个默认角色指向不同设备时使用 |
| C 所有活动播放设备回环 | 每个活动播放设备各开一路，去重后相加 | 解决“会议声音走非默认设备”；要避免同一来源被重复相加，设备增减需监听。Granola 对 Teams 的做法是只对 Teams 渲染会话所在的设备开回环（见 15.6），要靠进程名单；C 是不依赖会议软件的通用版本 |
| B 进程级回环 | `ActivateAudioInterfaceAsync` + `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`，排除自身进程树，听所有应用，不受默认设备切换影响 | **Teams 通话音频对它不可见**（15.6，OpenWhispr 实测）；各实现在空闲期的行为不一致；要求完成回调实现 `IAgileObject`、激活等待要设上限、格式要显式指定 |

  决策规则：先看“在 S1 的会议软件清单（Teams、Zoom、腾讯会议、飞书、钉钉、浏览器里的网页会议）上漏录次数为 0”；满足的方案里取最简单的。B 只做对照测试，除非它在清单上全部通过，否则不入选。无论选哪个方案，都必须带 5.10 的静默失效监测。

### 5.4 麦克风（我的声音）

- WASAPI 采集默认录音设备，48 kHz，多声道下混为单声道。默认角色取 `eCommunications`（OBS 的麦克风默认值，部分会议软件会选通信设备），设置里可改为 `eConsole` 或指定具体设备；两个角色指向不同麦克风时的行为由 S1 验证。
- 同样监听默认设备变化并重连。
- 没有麦克风时，画面和系统音照常录；托盘明确提示“无麦克风”，并在 `session.json` 里标记。

### 5.5 时间线修复：补静音与漂移修正

必须解决的两个问题，且必须用 60 分钟实测验证（S1）：

1. **空闲期无数据**：回环采集在没有声音播放时不出数据，时间线会被压缩，造成音画不同步。
2. **时钟漂移**：麦克风和声卡各用各的硬件时钟，一小时可漂几百毫秒。

做法：每个数据包带 QPC 时间戳 T（`IAudioCaptureClient::GetBuffer` 返回的 `qpcPosition`）。

- 期望采样数 `N_exp = (T − t0_stream) × 48000`，实际已写入 `N_act`，差 `Δ = N_exp − N_act`。
- `Δ` 超过正阈值：补 `Δ` 个静音采样；超过负阈值：丢弃多余采样。阈值带滞回，初值取 40 ms，由 S1 调定。
- 没有数据包期间（回环空闲），每 10 ms 检查一次，由 QPC 推算并补静音，保证时间线连续。
- **单次补静音过长要报警**：补静音本身照做（视频同样按 QPC 重复帧，保持对齐），但一次超过 5 秒就记一条 `large_gap` 事件并告警，因为这说明采集线程被饿死或设备停摆，不是正常的“没人说话”。睡眠本来就会结束本场（6.5），不走这条路径。

补充（参考 OBS 的 WASAPI 采集实现，具体取舍由 S1 实测决定）：

- **包标志**：带 `AUDCLNT_BUFFERFLAGS_SILENT` 的包按全零处理，不读缓冲内容；带 `AUDCLNT_BUFFERFLAGS_TIMESTAMP_ERROR` 的包，时间戳不可信，改用到达时间并计数；`DATA_DISCONTINUITY` 计入诊断，由 QPC 补齐。
- **时间源**：每一路设备各选一种——设备给出的 QPC 时间戳，或“包到达时间 − 包时长”。OBS 的默认是麦克风用后者、桌面音用前者。S1 在本机的多种设备（Realtek、HDMI、蓝牙）上比较抖动与漂移，每一路选定一种后写回本文。
- **空闲期保活**：OBS 为回环提供“静音修复”：另开一路共享模式的渲染流，持续写入全零缓冲，让回环在无声时也持续出包。本设计先用 QPC 补静音；S1 对比这两种做法（保活流可能影响蓝牙耳机的省电状态和设备占用），再选定。

### 5.6 编码与落盘

每轨一个 ffmpeg 子进程，从 stdin 读原始数据，写 Matroska。MKV 在进程被杀或断电后仍可播放到最后一刻。以下命令仅为示意，码控参数由 S3 调定：

```text
ffmpeg -f rawvideo -pix_fmt nv12 -s 1920x1080 -r 15 -i pipe:0 -c:v h264_nvenc -preset p4 -rc vbr -cq 28 -g 30 -f matroska video.mkv
ffmpeg -f f32le -ar 48000 -ac 1 -i pipe:0 -c:a flac -f matroska mic.mka
ffmpeg -f f32le -ar 48000 -ac 2 -i pipe:0 -c:a flac -f matroska system.mka
```

- 每轨一个写入线程，队列有界（视频约 1 秒，音频约 10 秒）。
- ffmpeg 使用 LGPL 构建（不含 libx264 等 GPL 组件），随安装包分发；开发时下载到 `vendor/ffmpeg/`（不入库）。
- 评估过但未选：Media Foundation 直接写 MP4（崩溃后能否恢复不明确；NVIDIA ShadowPlay 的 MP4 封装器里，收尾失败时有“删除畸形文件”的代码路径，见 15.6，算是不采用它的旁证）；链接 ffmpeg 库（Windows 上构建依赖 libclang，环境成本高）。

### 5.7 保存并结束（收尾）

1. 控制器进入“收尾中”。
2. 停止所有采集源，冲刷队列。
3. 关闭三个 ffmpeg 的 stdin，等待退出；10 秒仍未退出则强杀并记录。
4. 写入 `session.json`：结束时间、`end_reason`、`state=finalized`。
5. 托盘提示“已保存”（遵循 6.3 的静默规则）。
6. 后台生成 `meeting.mp4`：视频直接拷贝，两轨按偏移对齐后等增益相加并限幅，编码为 AAC。示意命令：

```text
ffmpeg -itsoffset <v_off> -i video.mkv -itsoffset <m_off> -i mic.mka -itsoffset <s_off> -i system.mka
  -filter_complex "[1:a]aformat=channel_layouts=stereo[m];[m][2:a]amix=inputs=2:normalize=0,alimiter=limit=0.95[a]"
  -map 0:v -map "[a]" -c:v copy -c:a aac -b:a 128k -movflags +faststart meeting.mp4
```

三轨文件在保存后几秒内即完整可用；`meeting.mp4` 稍后生成。

### 5.8 崩溃恢复

启动时扫描保存目录下 `state=recording` 的会话：

1. 对每个 MKV / MKA 做一次拷贝式修复；
2. 取各轨最后时间戳估算结束时间，`state=recovered`；
3. 补做 `meeting.mp4`；
4. 通知用户“已恢复上次中断的录制”。

同时扫描 `state=finalized` 但缺少 `meeting.mp4` 的会话，补做收尾。

### 5.9 背压与诊断

- 音频绝不丢；视频队列满时丢最旧帧。
- `session.json` 记录诊断计数：补静音总时长、丢弃采样总数、设备切换次数、编码器重启次数、受限区间（UAC / 锁屏）、`capture_silent` 与 `large_gap` 告警次数，以及按原因分类的画面帧统计（参考 Loom 的做法）：重复帧分为安全桌面 / 复制对象重建 / 复制失败，丢帧分为编码器 / 出错 / 入队 / 重同步。分原因计数，是为了出问题时能直接看出是哪一环。
- 每次录制开始时，往日志里写一份环境快照：显卡与驱动、选定的编码器、显示器与缩放、是否 HDR、DWM 状态、各音频设备与格式、两个默认角色分别指向哪个设备、所选回环方案。NVIDIA ShadowPlay 的采集库里也有一条格式化的环境诊断字符串（含 DWM、桌面捕获状态等）。事后排查“这场为什么没录好”，最需要的就是它。

### 5.10 采集健康监测（不静默失败）

回环采集有一类很隐蔽的失败：流是通的，数据也在写，写进去的却全是静音。OpenWhispr 的实测（见 15.6）是，Teams 通话的音频对进程级回环不可见，整场只录到“我”的声音，没有任何报错；Granola 也维护着一份“进程级回环听不到”的应用名单（新版 Teams、WhatsApp、8x8），并对 Teams 做输出设备探测。所以健康监测是必需项，不是优化项。

**音频：端点电平对照**（每秒一次，整场录制期间始终有效）

1. 读取每个活动播放设备的 `IAudioMeterInformation` 峰值，任意一个高于 0.01 记为“有声”。
2. 读取本轨这一秒内输出的峰值，高于 32/32768（约 −60 dBFS）记为“采到声音”。
3. 这一秒“有声”而“没采到”，不一致计数加一；**只要有一秒采到声音，计数清零**；连续 5 秒不一致，触发告警。同一次异常只告警一次，恢复后重新布防。
4. 不能因为“已经采到过一次声音”就永久解除。OpenWhispr 的实现一度栽在这里：开场的一声通知音让整场的检查失效，后半场静默录空。
5. 取不到电平表的机器不报告，也不猜。

告警动作：托盘变琥珀，写日志，`session.json` 的 `capture_silent` 加一，并弹出提示，指明哪个设备有声而没采到。**不自动切换采集方案**，由用户在设置里切换（见 5.3 的候选），避免悄悄改变录制行为。

**其他探测器**。Loom 的原生录制进程里有一整条“媒体异常检测流水线”，这里取同样的思路，阈值写进配置，由 S1、S2、S3 调定：

| 探测 | 判据 | 动作 |
|---|---|---|
| 设备挂起 | 采集设备连续 N 秒没有任何包或帧 | 重连；告警 |
| 时间戳间隙 / 重叠 | 相邻样本的时间戳差远大于或小于样本时长 | 计数；补静音或丢弃重叠；超限告警 |
| 持续低帧率 | 输出帧率长时间低于设定值 | 告警，并附带当时的 CPU 占用 |
| 单次补静音过长 | 一次补静音超过 5 秒（见 5.5） | 记 `large_gap` 并告警 |

**与睡眠、锁屏的关系**：所有基于超时的探测，在睡眠、锁屏、显示器关闭期间必须停用，恢复后重新布防（夸克的看门狗就是这样处理的），否则恢复后会误报。

## 6. 运行外壳

### 6.1 状态机

`待命 → 启动中 → 录制中 → 收尾中 → 待命`

- 所有命令（开始 / 保存 / 退出）进入同一个控制器线程串行处理；500 ms 内的重复触发被忽略。
- “启动中”失败（磁盘不可写、所有采集源都打不开等）直接回到待命并提示，不留半成品会话。
- 目标：热键到开始写入不超过 1 秒。采集立刻开始，ffmpeg 就绪前的数据先在内存队列里排队。
- 后台任务（remux、转写等）不属于这个状态机，由后台任务单独跟踪；上一场处理时可以直接开录下一场。

### 6.2 热键

| 动作 | 默认 | 说明 |
|---|---|---|
| 开始录制 | `Ctrl+Alt+R` | 待命时生效；录制中无效果 |
| 保存并结束本场 | `Ctrl+Alt+S` | 录制中生效；待命时无效果 |
| 保存并退出程序 | `Ctrl+Alt+Q` | 录制中先保存再退出 |

- 三个动作均幂等。静默程序没有界面，单键切换容易按两下把刚开的录制停掉。
- 基于 Tauri v2 的 global-shortcut 插件（底层为 `RegisterHotKey`）。启动时逐个检测注册是否成功，被其他软件占用就提示，并在托盘菜单里标出。
- 开发机装有 NVIDIA App / ShadowPlay，其默认热键为 Alt 系列，与上述默认值不冲突；S5 仍需实测。
- **常驻注册还是按状态注册**：Loom 注册前先检查该组合是否已被占用，并且只在录制期间才注册“停止”类热键。本设计默认三个热键常驻，原因是幂等：开始键按两下，第二下若已被注销，就会漏给前台软件。S5 评估按状态注册能否减少对其他软件的干扰，结论写回本文。
- **热键机制不止一种**：ShadowPlay 的热键放在独立的 helper 进程里，同时用 `RegisterHotKey`、Raw Input 和 `GetAsyncKeyState`，经内存映射文件与命名管道转发（见 15.6）。推断是为了覆盖全屏游戏与按键说话，会议场景用不到，但 S5 要实测“全屏独占 / 管理员窗口在前台时热键是否生效”，生效不了就明确提示，而不是换一套机制悄悄兜底。

### 6.3 提示与静默程度

- **安静（默认）**：没有任何弹窗和提示音，只有托盘图标变化：灰（待命）、红点（录制中，悬停显示时长与文件大小）、琥珀（有轨道中断或其他告警）。共享屏幕时，对方最多只可能看到托盘里的小图标。
- **标准**：另加开始 / 保存的气泡通知。
- **出错一定弹提示**，两种模式一样。
- 不提供“完全隐形”模式：托盘图标始终存在，出错一定提示。静默录丢一场会议，比多一个小图标糟得多。
- Windows 自带的麦克风使用图标无法关闭，这是系统行为。

### 6.4 托盘与窗口

- 托盘菜单：开始 / 保存并结束 / 打开录音文件夹 / 设置 / 打开日志 / 开机自启 / 退出。
- 设置窗口（网页界面）仅在点开时创建。
- 首次运行弹向导：选保存目录、确认热键、是否开机自启。

### 6.5 自动保护

- 单场上限 6 小时（可改），到点自动保存并结束。
- 磁盘剩余空间低于 5 GB（可改）时，自动保存并结束。
- 睡眠视为“结束本场”：先保存；唤醒后回到待命，并提示“因睡眠已保存”。
- 关机、注销：先保存再退出。

### 6.6 其他

- **单实例**：再次启动只会唤起已运行实例的设置窗口，避免两个实例抢热键和设备。
- **开机自启**：Tauri autostart 插件，默认关闭，由向导询问。
- **采集线程**：普通线程 + 事件句柄 + MMCSS（任务名 `Audio`），不使用 RTWQ 工作队列。OBS 的源码里记录了 RTWQ 在桌面音上会静默失败，因此被它关掉。其余细节在实施计划里定。

## 7. 语音管线与发言人识别（子项目 B）

### 7.1 触发与资源

- “保存并结束”后自动投递语音任务；设置里可改为手动触发。
- 任务在独立的 `speech-sidecar` 进程里以低优先级运行，只用 CPU，限制线程数，不影响正在进行的录制。
- v1 不做 GPU 加速。FunASR 官方讨论区的基准里，SenseVoice-Small 在 CPU 上约 17 倍实时（厂商自测，仅供参考，以 S4 实测为准）。不用 GPU 也避开了 Blackwell 显卡的 CUDA 兼容风险。
- Rust 侧使用官方 `sherpa-onnx` crate（v1.13.8，覆盖离线 ASR、VAD、离线说话人分离）。社区的 `sherpa-rs` 已声明停止维护，不使用。

### 7.2 流水线

输入是无损分轨 `mic.mka` 和 `system.mka`：

1. 解码并重采样到 16 kHz 单声道。
2. **回声消除**：以系统音轨为参考处理麦克风轨，去掉外放时被麦克风录进去的对方声音，否则对方的话会被记到“我”头上。候选实现为纯 Rust 的 `corti-aec`（离线 NLMS）和 `aec3`（WebRTC AEC3 移植），由 S4 择优。原始轨始终保留，清理结果另存。同类产品 Jamie 的录音进程是在采集端实时做 WebRTC AEC3（以回环为参考）并混成 48 kHz 单声道（见 15.6）；本设计不这样做，采集阶段只存原始音频（理由见 5.1），好处是算法升级后可以对旧录音重跑。
3. **系统音轨**：先说话人分离（pyannote segmentation 3.0 + 3D-Speaker 中文声纹模型 + 聚类），得到“谁在什么时间段说话”，再对每个单人片段逐段识别。先分人再识别，避免一段话里混着两个人。
4. **麦克风轨**：VAD 切段，再识别，全部标为“我”。
5. **识别引擎**默认候选为 SenseVoice-Small（int8），自带标点和数字规整；备选 Paraformer + 标点模型、Fun-ASR-Nano（LLM 类模型，更适合 GPU，走 Python 栈，通过 sidecar 协议接入）。默认值由 S4 在真实中文会议录音上的对比结果决定。
6. 按绝对时间合并两轨，输出 `transcript.json`。

### 7.3 发言人模型

- “我”= 麦克风轨，几乎不会判错。
- 对方自动编号为“发言人 1 / 2 / 3…”。
- 点名字即可改名，改一次整场生效；可合并被误拆的两个人；可指定实际人数后重新聚类。段级声纹向量缓存在会话目录的 `diarization.cache`，重新聚类不用重跑模型。
- 每个发言人的声纹质心向量存进数据模型，以后做“跨会议自动认人”时，旧录音不用重新处理。
- 已知限制：混合会议里几个人共用你的麦克风时，麦克风轨有多个人，v1 仍统一标为“我”；给麦克风轨也开说话人分离的开关预留，效果待实测。

`transcript.json` 结构示意：

```json
{
  "version": 1,
  "session": "2026-10-13_203000",
  "engine": { "asr": "sensevoice-small-int8", "diarization": "pyannote-3.0+3dspeaker", "aec": "corti-aec" },
  "speakers": [
    { "id": "me",   "name": "我",      "source": "mic" },
    { "id": "spk1", "name": "发言人1", "source": "system", "centroid": "<base64 float32[]>" }
  ],
  "segments": [
    { "start": 12.34, "end": 15.80, "speaker": "spk1", "track": "system", "text": "……" }
  ]
}
```

### 7.4 引擎协议

`speech-sidecar` 与主程序之间只有一个进程协议：标准输入输出上的 JSON 行。换引擎只需实现同一协议，主程序不用改。

```json
{"cmd":"process","session_dir":"E:\\...\\2026-10-13_203000","config":{"asr":"sensevoice-small-int8","aec":true,"diarize_mic":false,"num_speakers":null}}
{"event":"progress","stage":"asr","pct":0.42}
{"event":"done","transcript":"transcript.json"}
{"event":"error","code":"model_missing","message":"..."}
```

### 7.5 模型管理

首次使用时一次性下载，合计几百 MB，校验哈希，放在 `%LOCALAPPDATA%\record\models\`，之后完全离线。下载失败会明确报错并可重试，不会悄悄跳过。分发前核对各模型的许可（个人自用不受限）。

## 8. 会后处理（子项目 C）

- **纪要**：把带发言人名字的转写稿交给大模型，生成 `summary.md`（议题、结论、待办含负责人、关键数字）。长会议先分段总结再汇总。改了发言人名字后可一键重新生成。
- **模型接入**：同一个接口，两种实现：本地 Ollama（默认）；OpenAI 兼容接口（用户自己的 Key，存进 Windows 凭据管理器，不写配置文件）。**只发文字，不发音视频**。云端默认关闭，首次启用时明确提示。
- **检索与导出**：转写稿存入 SQLite，用 FTS5 做全文检索（中文用 trigram 分词），可跨会议搜“谁说过什么”。可导出 `.md`、`.srt`、`.txt`。

## 9. 错误处理

总原则：不静默失败，不丢已录数据。任何异常都会写日志、记入 `session.json` 诊断、让托盘变琥珀色并弹提示。

| 情形 | 处理 |
|---|---|
| 默认音频设备变化或拔出 | 自动重连新设备并补静音；设备丢失后每 3 秒重试一次（OBS 的重连间隔）；10 秒仍未恢复则该轨标记“中断”并提示，其他轨继续；后台仍每 3 秒重试，恢复后接续，空档补静音 |
| 回环“通但全是静音”（`capture_silent`）、设备挂起、补静音过长（`large_gap`） | 托盘变琥珀、写日志、弹提示并指明是哪个设备；不自动切换采集方案，由用户在设置里切换（见 5.10） |
| 显示模式变化 / Desktop Duplication 失效 | 重建采集（尝试带节流，见 5.2）；输出尺寸不变（缩放加黑边）；重建期间重复上一帧 |
| UAC / 锁屏安全桌面 | 抓不到属系统限制；重复上一帧并记录区间 |
| 编码器或 ffmpeg 异常退出（如显卡驱动重置） | 自动重启一次（新分段）；仍失败则该轨标记中断并提示 |
| 没有硬件编码器 | 启动时明确报错；由用户在设置里显式选软件编码，不悄悄降级 |
| 磁盘写满 / 写入失败 | 立即保存并结束，已有数据完好 |
| 程序崩溃 / 断电 | 下次启动自动修复并生成 MP4（见 5.8） |
| 热键注册失败 | 提示，并在托盘菜单标出；菜单操作仍可用 |
| 语音任务失败（模型缺失、sidecar 崩溃等） | 标记失败、显示原因、可重试；不影响录制和原始文件 |
| 睡眠 / 注销 / 关机 | 见 6.5 |

- 合成信号源：生成已知时间戳的蜂鸣与色块，不依赖真实设备，用于测补静音、漂移修正、对齐、混音。

- 崩溃恢复测试：录制中强杀进程，重启后产物可播放。

### 10.3 真实验收

开一场真实会议：热键开始，30–60 分钟后保存，检查画面、声音、同步、转写稿与发言人。

### 10.4 子项目 A 的完成标准

- 热键可开始与保存；静默无弹窗；托盘状态正确。
- 60 分钟录制：无丢音，音画偏差 ≤ 80 ms，CPU 占用 < 5%，文件可播放。

- 设备切换、锁屏、睡眠、磁盘不足等情形按第 9 节行为。

## 11. 实施拆分

每个子项目单独走“设计 → 计划 → 实现”。

- **子项目 A：静默录屏器**（采集 + 外壳 + 落盘 + 收尾 MP4 + 崩溃恢复）。做完即可日常录会议。子项目 A 不引入数据库：会话状态以 `session.json` 为准，启动时扫描修复。

- **子项目 C：会后处理**（纪要 + 搜索 + 导出）。
- **以后再说**：声纹库跨会议认人、按窗口录制、自动检测会议开始、macOS。

### 15.3 OBS Studio 的采集与封装（读源码）

以下是阅读 OBS 源码得到的观察，已折算进第 5、6、9 节：

- **音频角色**：桌面音取 `eConsole`，麦克风取 `eCommunications`。
- **回环静音**：提供“静音修复”——另开一路共享模式的渲染流，持续写入全零缓冲，让回环在无声时也出包。
- **包处理**：`SILENT` 标志的包按全零处理；`TIMESTAMP_ERROR` 只写日志。
- **时间源**：有 `use_device_timing` 开关，默认麦克风关（用到达时间 − 包时长）、桌面音开。
- **格式**：不设置自动转换，取设备混音格式转成 float 后自行重采样。
- **线程**：RTWQ 因在桌面音上静默失败而被禁用；采集线程用 MMCSS（任务名 `Audio`）。
- **重连**：设备丢失后每 3 秒重试一次。
- **画面**：默认 Desktop Duplication；只在多显卡或显示器匹配不上时才用 WGC（WGC 提供强制 SDR 选项）。以 0 超时调用 `AcquireNextFrame`；`ACCESS_LOST` 重建；`WAIT_TIMEOUT` 沿用上一帧；重建节流常量 3 秒；`DuplicateOutput1` 同时请求 FP16 与 BGRA8 两种格式并带 HDR 标志。
- **封装**：用独立的 muxer 进程（`obs-ffmpeg-mux`），主进程通过 stdin 管道送数据。与本设计“采集进程 + ffmpeg 子进程 + 管道”同构，算是一条旁证。

### 15.4 夸克网盘 7.3.5 的录音功能（闭源，仅架构层面）

分析对象是本机已安装的夸克网盘（Electron 应用，带自己的 Chromium 分支）。只读取了录音相关的 JS（主进程和两个录音窗口，约 10 MB）。

**证据强度要分清**：REA 的结构化结果只覆盖应用级结构——1 个主进程入口、2 个录音渲染入口、2 个 Worker、17 个存储访问节点、67 个端点与路由节点（其中混有 `days`、`hours` 之类的误报）。三个最大的压缩 bundle（主进程和两个录音窗口）在语义分析阶段耗尽了堆，把堆放大到 8 GiB 也没有解决（见 15.5），所以下面关于采集 API、音频处理链、错误类型等细节，来自对压缩代码的关键字与上下文读取，没有 REA 语义图的佐证。以下是观察，不含代码：

- **采集用 Web API，不是原生 WASAPI**：麦克风用 `getUserMedia`，系统声音用 `getDisplayMedia`（仅音频）。两路请求里都打开了浏览器的回声消除和降噪。本设计在采集阶段不做任何处理，理由见 5.1。
- **音频处理链**：两路汇入同一个 Web Audio 节点，`AudioWorklet` 按固定大小（2560 采样）分块取出 PCM；`MediaRecorder` 用默认参数分块、追加写入本地文件。追加式写入对崩溃友好，与本设计选 MKV 同理。
- **没有分轨**：两路混合后一起处理，说话人区分只能靠云端。本设计分轨保存，能直接得到“我 / 其他人”。
- **云端实时转写**：PCM 经 WebSocket 推到云服务。录音模块定义了专门的错误类型：断网、长时间无声（`VOICELESS_ERROR`）、录音超时（`RECORDING_OVER_TIME`）、额度限制（`TRANSLATE_LIMIT_ERROR`，按名称推断）、设备被占用（`OCCUPIED_ERROR`）、麦克风异常、系统权限。可作为第 9 节的对照清单。
- **麦克风断开**：轨道结束 50 毫秒后，若仍在录制且流已失活，就向界面报告“麦克风错误”并上报埋点。这个处理器里没有重新取流的逻辑，界面层是否重试没有确认。本设计在采集层自动重连。
- **会议检测靠进程名**：内置 4 条规则（`Feishu.exe`、`WeMeetApp.exe` 及其小写写法、`tblive.exe`，依次是飞书、腾讯会议，以及推测为淘宝直播的进程），并支持从云端下发配置。与 Notion 的“枚举音频会话”相比更简单，但依赖名单。
- **界面**：紧凑悬浮窗、展开窗、实时字幕窗、权限引导窗、断网提示窗，全是可见窗口，与本设计的“静默 + 托盘”相反。
- **热键**：这几份代码里没找到录音相关的全局热键。`hotkey` 命中的是编辑器快捷键表，`accelerator` 命中的是“游戏加速”窗口和 MIME 类型。这只是“没找到”，不是“不存在”。
- **看门狗与电源**：主进程每 10 秒向主窗口发一次 ping，回应慢于 500 毫秒就上报“卡死”；锁屏、睡眠、关机期间停用，解锁、恢复后启用，避免误报。这个看门狗盯的是界面响应，与录音无关。可借鉴的一点：任何基于超时的自检，都要在睡眠和锁屏期间停用，否则恢复后会误报。
- **本地识别能力**：安装目录带本地 ASR 库和 ONNX Runtime，主进程有本地 ASR 开关；目前只看到它用在网页内容提取上，录音转写是否也用它，没有确认。

### 15.5 REA 在这台机器上的能力边界（实测）

- **Electron / JS 应用**：`analyze-javascript-application` 可直接分析 `app.asar` 或解包目录，不需要外部引擎。Notion（asar，约 10 MB）完整跑通。
- **大体积压缩 bundle**：分析 worker 的堆默认 1024 MiB，单文件超时 300 秒。夸克的三个单行压缩 bundle（2.7 至 4 MB）在语义阶段耗尽堆。用 `--max-heap-mb 8192 --analysis-timeout-ms 1500000` 重跑，每个文件约 6 分钟后仍然耗尽，产出的语义图与默认参数下一模一样（6416 个节点、5394 条关系）；内存一路涨到撞线，没有收敛迹象。后来又把堆放到参数上限 16384 MiB，并且只分析录音窗口那一个文件（约 2.7 MB）重试：11 分 17 秒后仍在语义阶段耗尽堆，语义图只剩 1 个节点、0 条关系、12 个未知项，应用图 42 个节点、52 条边，覆盖状态均为“部分”。结论：对这几个文件放大堆没用，REA 只能给出部分覆盖。**不能把原因简单归为“文件大”或“单行”**：后来分析的 Granola 主进程包更大（6.8 MB，最长一行 3.6 MB），12 GiB 堆下 1 分 44 秒就跑完了（见下）。夸克这几个文件为什么会让语义阶段耗尽堆，没有查明。
- **普通 Electron 应用的对照**：tl;dv（asar 36 MB、1158 个文件、约 214 万个 AST 节点）用 8 GiB 堆约 1 分钟跑完，覆盖状态为“部分”：识别出 1 个主进程、53 个渲染端节点、3 个原生插件、57 个 IPC 操作（其中 35 个是字面量通道）；窗口、预加载、主进程处理器都识别为 0，多半是打包后的别名造成的漏识别（推断），不等于不存在，所以窗口、热键等细节仍然靠关键字与上下文读取。
- **Granola（asar 70 MB、953 个相关文件、约 662 万个 AST 节点）**：第一次被 REA 拒绝，原因是 asar 里登记的几个原生模块的哈希，与解包出来的文件对不上（打包之后又对 `.node` 做了代码签名，是常见情形；安装包整体哈希已按官方清单核对过）。REA 默认中止，并提示可以用 `--integrity-policy record-and-continue`，这些文件会按“不可信字节”保留，这个保护是合理的。加上该参数、堆设为 12 GiB 后，1 分 44 秒跑完，覆盖状态为“部分”：识别出 1 个主进程、1 个渲染端、9 个原生插件节点、11 个 IPC 操作（只有 2 个是字面量通道）；窗口、预加载入口、工具进程、原生插件绑定都是 0。而主进程里实际有若干个工具进程和一个 Rust 原生模块，说明 REA 的结构化结果在打包后的代码上漏识别明显，采集细节依然要靠关键字与上下文读取。
- **自带 Chromium 分支、API 名不是 `electron` 的应用**（如夸克）：窗口、IPC、预加载分析全是 0，这不等于不存在，需要配合关键字与上下文读取。
- **特性追踪**：`trace-application-feature` 可在已有证据上，以路由 / 字符串 / API / 通道 / 模块为种子追踪。对夸克得到的是应用级结构（入口、窗口、Worker、存储、端点），不含函数级调用关系。
- **原生 Windows 程序**：深度分析（`search`、`decompile`、`xrefs`）需要 Ghidra 12.1.x 加 64 位完整 JDK 21，或 IDA；Hopper 在 Windows 上不支持。没有引擎时，`inspect-artifact`、`inspect-pe-resources` 只能给出清单层面的信息。
- **Ghidra 的安装与实测**：Ghidra 12.1.4 与 Temurin JDK 21.0.12.1 都从官方发布页下载、核对哈希，放在 `E:\gezi\tools\`；只在命令行进程里设置 `GHIDRA_INSTALL_DIR`、`JAVA_HOME`，不改系统环境变量。`rea doctor` 里 Ghidra 的各项检查（路径、版本、headless、原生反编译器、Java、原生沙箱控制）全部为健康。对 1 至 4 MB 的 DLL，`search` 每次调用约 40 至 80 秒（含导入与自动分析），`--snapshot` 没有让第二次调用明显变快；总期限由 `REA_GHIDRA_STARTUP_TIMEOUT_MS` 控制，默认 330 秒，本次设为 30 分钟。无符号的程序上，过程名搜索基本只返回导入导出项，架构级结论主要靠字符串，本次没有做反编译。NVIDIA ShadowPlay 的 9 个组件按这个方式分析，结果见 15.6。
- **环境**：`rea doctor` 整体仍是 `healthy=false`（IDA 等其他引擎未配置、配置漂移），但 Ghidra 一项已健康；没有执行 `rea setup`，因为它会改写各 agent 的配置。

**OpenWhispr（MIT）：系统音采集的一手实测**

- 背景：OpenWhispr 是 Electron 应用，v1.7.4 起用原生 Windows helper 采集“所有应用、所有输出设备”的系统音（进程级回环，排除自身进程树，PR #960）。
- 回归：[issue #1265](https://github.com/OpenWhispr/openwhispr/issues/1265)（Windows 11 25H2，build 26200.8655，与本开发机同一大版本）：Teams 会议录不到对方声音，蓝牙耳机、内置扬声器、关闭独占模式都一样。用户的绕过办法是会议开始后把扬声器切到虚拟声卡（NVIDIA Broadcast），或在播放设备属性里把某个“增强”选项切一下再切回（据称约四分之三的情况有效）。
- 修复一：[PR #1866](https://github.com/OpenWhispr/openwhispr/pull/1866)（改用端点回环，理由是 Teams 用独占模式）已关闭，没有合并。
- 修复二：[PR #2233](https://github.com/OpenWhispr/openwhispr/pull/2233)（2026-09-30 合并）给出了更完整的实测。作者在 Windows 11 虚拟机里对一场真实 Teams 通话同时测量：他们发布的 helper（排除自身进程树）峰值 0.0000，持续 15 秒；进程级回环指向 Teams 的音频进程、指向 Teams 进程树根，也都是 0.0000；**端点回环 0.38–0.65**。15 种配置（s16 24k / 48k、float32、单声道 16k，有无 `AUTOCONVERTPCM`，事件驱动与轮询）结论一致，同一时刻的对照音都能采到（0.25–0.36）。Teams 的会话是普通共享模式，在 `IAudioSessionManager2` 里可见、属于 `ms-teams.exe`（不在被排除的进程树内），重启整个音频栈也没用。结论：Windows 对进程级回环隐藏了 Teams 通话音频；“独占模式”的解释不成立（端点回环同样采不到独占流，却采到了 Teams）。
- 静默检查的缺陷：他们的 helper 在**第一次听到任意应用的声音后就永久解除**对比，开场一声通知音就让整场的检查失效，Teams 的入会提示音同样会触发。修复为整场每秒对比，连续 5 秒“端点有声、采集没听到”才告警，采到声音就清零，同一次异常只告警一次，取不到电平表的机器不报告。→ 5.10。
- 他们的处置：告警后由主程序把系统音切换到 Chromium 的回环采集（只听默认设备）。本设计不自动切换（5.10）。
- 为什么不直接全用端点回环：PR 作者指出端点回环只听默认输出设备，而这正是进程级回环要解决的限制。→ 5.3 的方案 C。
- 这些是别人在别的机器上的实测，本机结果以 S1 为准。

**Jamie 5.7.21（Tauri 2.10 + C++ 录音进程）**：技术路线和本设计最接近。

- 主程序是 Rust + Tauri 2.10，插件有 autostart、deep-link、dialog、fs、log、notification、opener、os、shell、single-instance、store、updater，另有托盘。**没有 global-shortcut 插件，也没有 `RegisterHotKey`。** 录音进程作为 sidecar，由 shell 插件拉起（`spawn`、`stdin_write`、`kill`）。
- 录音进程 `audio_recorder_streaming.exe`（12 MB）是 C++，链接了 libwebrtc。模块有 `audio_source_win`（WASAPI 采集）、`audio_manager_win`、`notification_client`（设备变更通知）、`audio_mixer`（48 kHz 单声道）、`resampler`、`wav_writer`、`webrtc_client`（Opus 编码并经 WebRTC 推流）。
- WASAPI 细节（来自日志文案与字符串）：先尝试 RAW 模式（`SetClientProperties(RAW)`），失败或采样率变化时有回退日志；设备变化时重新初始化 audio client；对静音缓冲计数；使用 MMCSS（`Pro Audio` 任务类）；取不到混音格式有专门处理。
- 回声消除：混音器里有 `process_capture_with_aec`，用 WebRTC AEC3 在采集端实时处理麦克风。
- 系统音方案：字符串与导入名里没有 `ActivateAudioInterfaceAsync` 和进程级回环常量，推断用的是设备级回环。
- 对本设计：验证了“Tauri 主进程 + 独立录音子进程”的路线；RAW 尝试与回退、MMCSS、设备通知后重初始化，与 5.3 至 5.5 一致；采集端实时 AEC 与本设计的取舍不同（5.1、7.2）。

**Loom 0.379.4（Electron + 原生录制进程）**：

- 主进程是 Electron，真正的采集在 `loom-recorder-production.exe`（7 MB，C++，源文件路径留在字符串里）；主进程按平台拉起它，并上报它的 CPU 占用。
- 画面：统计项名为 “data duplication” 的采集路径（推断为 Desktop Duplication）、GDI 视频源、共享内存视频源；缩放与转色用 Intel IPP；编码经 Media Foundation（有 `use_hw_encoder`、`force_software_encoder`）；封装是自写的 TS / HLS 分片（音视频可分开写），另有鼠标事件、摄像头气泡事件的分段器。
- 音频：类名 `WasapiSourceV2`；导入名里没有进程级回环的 API，推断为设备回环；有 `AudioLoopbackGlitch` 异常类型，并处理 `AUDCLNT_S_POSITION_STALLED`。
- **健康监测（最值得借鉴）**：重复帧、丢帧都按原因分类计数——重复帧分安全桌面、重建、复制失败，丢帧分编码器、出错、入队、重同步；异常检测流水线包含 PTS 间隙、PTS 重叠、采集设备挂起、持续低帧率、高 CPU 加掉帧、音频“安静设备”（dB 阈值）；阈值通过远程特性开关下发。→ 5.9、5.10。
- 热键：Electron `globalShortcut`；组合键取自用户偏好，注册前先检查占用；只在录制期间有效的快捷键，在开始录制时注册、结束时注销。→ 6.2。
- 会议检测：Windows 版的原生检测模块几乎是空壳，主进程里有“Windows 不支持”的分支（推断）。

**tl;dv 3.0.264（32 位 Electron + 自带 ffmpeg）**：

- 画面与系统音：`setDisplayMediaRequestHandler` 取**第一块屏幕**加 `loopback` 音频；只请求音频时只给 `loopback`。这是 Chromium 的回环，只听默认播放设备。
- 自带 `ffmpeg.exe`（79 MB），用来把录下的内容转成 HLS 分片并上传：H.264 720p、默认 18 fps、CRF 28、码率上限 1.5 Mbps，AAC 96 kbps / 48 kHz / 立体声，分片约 2 秒。输入是文件还是实时管道，没有确认。
- 热键：`Ctrl+.`，只用来标记“精彩片段”。
- 会议检测靠三个自研原生插件。`mic-activity`：只导入 COM 与 `QueryFullProcessImageNameW`，没有注册表 API，推断是枚举音频会话并查进程路径。`uia`：用 UI 自动化在 Teams、Zoom 窗口里找到“会议信息”按钮并**点击**，读出标题与链接。`accessibility`：WinEvent 钩子监听 Zoom 窗口。后两个会去操作别的软件的界面，本设计不采用。
- 发言人：转写在云端，客户端只提供改名接口；声纹功能有单独的“同意”接口（`voice-printing-consent`）。将来做跨会议声纹库，必须先取得同意（第 14 节）。

**Granola 7.637.0（Electron + Rust 原生模块；只录音，不录屏）**：

- 结构：Electron 主进程，加若干独立的工具进程（本地转写、本地说话人分离、听写、麦克风监测、音频采集）。原生部分是 Rust：`granola.native.windows` 用 napi 2.16 与 `windows` 0.60 crate，模块有 `audio_capture`（含重采样）、`device_render_loopback`、`render_sessions`、`device_info`、`process_list`。随包还有键盘钩子服务（`SetWindowsHookEx`）、Chrome 的 native messaging host（Go 写的，经命名管道通信）、第三方会议自动化程序、虚拟摄像头组件。只读了字符串和主进程脚本，没有运行。
- **系统音：默认是设备回环，进程级回环是受控开关。** 主进程里的源选择函数只有两个结果：`loopback`（默认）与 `loopbackAllDevices`。只有开关 `windows_loopback_all_devices`（默认关）打开、系统版本号 ≥ 19041、当前没有“已知听不到”的应用、且麦克风使用检测可用时，才选后者。`loopbackAllDevices` 的底层实现是推断：它要求的最低版本与进程级回环 API 的最低版本一致。
- **“已知听不到”名单**（开关 `windows_process_loopback_blind` 的默认值，可远程下发）：新版 Teams（`com.microsoft.teams2`）、WhatsApp、8x8 Work。这与 OpenWhispr 对 Teams 的实测互相印证。这类应用退出 20 秒后才切回。
- **对 Teams 的专门处理**（两个开关默认都关）：`windows_teams_device_loopback` 打开后，对 **Teams 渲染会话所在的那个设备**开设备回环；`windows_teams_output_monitor` 打开后，每 30 秒（发现不一致后每 5 秒）探测 Teams 相关进程（`ms-teams.exe`、`ms-teams_modulehost.exe`、`msteamsvdi.exe`、`msedgewebview2.exe`）的活动渲染会话：在哪个设备、峰值多少，同时取系统的默认设备与默认通信设备。最响的会话不在被采集的设备上，就记一条“输出设备不一致”日志；默认设备变化时重新获取系统音；连续 5 次探测失败就停止探测。读到的代码里，不一致**只记日志，不自动切换**。→ 5.3、5.10。
- 会议检测：靠“哪些应用正在使用麦克风”，来自音频会话的激活、失活、过期、消失事件（带会话 ID、进程 ID、进程名），可执行文件名再映射成应用标识。另有 UI 自动化、第三方会议自动化程序、Chrome 的 native messaging host。其中第三方会议自动化程序会去操作 Zoom、Teams 的界面（选摄像头、复制邀请链接、轮询花名册），本设计不采用。
- 发言人：Teams、Zoom 的说话人走独立的 Windows 子进程读取“花名册”（推断是读界面元素），不是声纹；声纹相关开关 `voice_fingerprint_*` 默认关。
- **本地转写与说话人分离（对子项目 B 有直接参考价值，不构成结论）**：转写用 sherpa-onnx（Windows x64 的 Node 绑定加 C API 动态库），引擎有 Parakeet（NeMo transducer，BPE，2 线程，CPU，支持热词）和 Whisper（独立的 `whisper-server` 进程）；说话人分离用 pyannote segmentation 3.0（ONNX）、WeSpeaker ResNet34（int8 ONNX）、PLDA（pyannote “community-1” 一套）、谱聚类（最多 32 人，种子固定），另有 VAD。模型与库按平台下载，文件名与 SHA-256 写死在客户端里，加载前逐个校验。转写与分离各在独立的工具进程里，有“跟不上实时”的事件。
- 本地存储：`better-sqlite3-multiple-ciphers`，即带加密的 SQLite。
- 热键：只有 `Alt+Space`（快速对话）和一个仅 macOS 的组合，用 Electron `globalShortcut`，注册失败写日志。
- 对本设计：独立印证了“进程级回环对 Teams 不可靠，默认走设备回环”；Teams 的输出设备探测给 S1 提供了现成的清单与做法；它的探测只记日志，与本设计“只告警、不自动换方案”的取向一致；B 阶段的引擎选型（sherpa-onnx、pyannote 分割、WeSpeaker 嵌入）有了同类产品的先例。

**NVIDIA ShadowPlay 11.0.9.251（REA + Ghidra；原生 C++，多进程多 DLL）**：

- 画面：NvFBC（NVIDIA 专有的帧缓冲捕获，支持按进程建会话；会话失效时有“重建 N 次仍失败就停止采集”的逻辑，受保护内容有专门的错误码），直接喂给 NVENC（H.264、HEVC、AV1）。HDR 采集依赖编码器支持 ARGB10 输入和 10 位编码，不支持时有专门的日志。NvFBC 对第三方不可用，本设计用 Desktop Duplication 加 ffmpeg 的 NVENC。
- 音频：NVIDIA 自己的 `nvAudCap` 库（接口带版本回退，日志里有“回环模式下启动音频重定向失败”）。
- 封装：自写 MP4 封装器，实现为 Media Foundation 的媒体接收器，音频 AAC；收尾失败时有“删除畸形文件”的代码路径。
- 即时回放：保存时才“解析偏移”，有总开关。
- 热键：独立 helper 进程（由 LocalSystem 服务插件在用户会话里拉起），同时用 `RegisterHotKey`、Raw Input（按键说话）和 `GetAsyncKeyState`，经内存映射文件、命名管道、消息总线转发；注册冲突有专门错误码；客户端连接有重试次数上限。
- 采集库里有一条格式化的环境诊断字符串（DWM、桌面捕获状态等）。
- 方法与限度：用 REA 的 `search` 取字符串和导入项，没有反编译；所有调用关系都是推断。

**没能分析的**：Fathom 1.42.6 的官方安装包托管在 `storage.googleapis.com`，本机网络连不上，没有下载，也就没有分析。

**这些调研改变了设计的哪些地方**：

1. 系统音的回环方案从“只有 A”改成四个候选加决策规则，进程级回环降为对照项（5.3）。OpenWhispr 的实测与 Granola 的“听不到”名单互相印证，两家的默认都是设备回环。
2. 新增整场有效的静默失效监测，只告警、不自动换方案（5.10）。
3. 诊断计数按原因分类，每次录制写环境快照（5.9）。
4. 单次补静音过长要报警（5.5）。
5. 热键注册策略与全屏、管理员窗口的实测列入 S5（6.2）。
6. 不做静默兜底（5.2、5.10）。
7. 采集端是否做回声消除，有了同类产品的对照（7.2）。
8. 将来做“自动检测会议开始”时的三条路线：枚举音频会话（Notion；Granola 读到了会话激活与失活事件的处理；tl;dv 为推断）、进程名名单（夸克）、UI 自动化操作会议软件界面（tl;dv、Granola，本设计不采用）。
9. 子项目 B 的引擎选型（sherpa-onnx、pyannote 分割、WeSpeaker 嵌入、谱聚类、模型哈希校验、独立进程）有了 Granola 这个同类产品的先例；是否采用仍由 S4 实测决定。
